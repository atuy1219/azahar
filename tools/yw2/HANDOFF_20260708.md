# YW2 / Busters local-wireless debug handoff

Date: 2026-07-08
Branch: `test/yw2-blasters-stub`
Repo: `atuy1219/azahar`

## Goal

Debug Yo-kai Watch 2 / Busters local-wireless room launch failure in Azahar Android.

Long-term target: make the Busters/local-wireless stage launch path work reliably enough to continue into the game instead of returning/failing shortly after the final proceed button.

## Current confirmed behavior

Observed on Android Azahar with YW2/NWM trace patches:

1. Room creation reaches `InitializeWithVersion`.
2. Game calls `Bind` on channel `243` with receive size `0x2E30`.
3. Game calls `SetProbeResponseParam`.
4. Game calls `BeginHostingNetwork` successfully.
5. Host status becomes `ConnectedAsHost` / status `6`:
   - self node: `1`
   - total nodes: `1`
   - max nodes: `4`
   - node bitmask: `0x1`
   - changed nodes initially: `0x1`
6. Game calls `GetChannel` successfully.
7. Beacon `SendPacket type=0 channel=11 size=435` continues periodically.
8. User presses the final proceed/next button.
9. About 3 seconds later the game calls `DestroyNetwork`.
10. Failure becomes visible roughly 2.7 to 2.8 seconds after `DestroyNetwork`.

Important: the time between `GetChannel` and `DestroyNetwork` is mostly menu-operation time and must not be treated as a network timeout. The meaningful interval is from `BEFORE_PRESS_NEXT` / actual button press to `DestroyNetwork`.

Representative timing:

```text
BEFORE_PRESS_NEXT: 1783488238.605
DestroyNetwork:    1783488241.597
AFTER_FAIL:         1783488244.403

BEFORE_PRESS_NEXT -> DestroyNetwork = about 2.99s
DestroyNetwork -> AFTER_FAIL        = about 2.81s
```

## Critical interpretation

During the roughly 3-second window after pressing proceed and before `DestroyNetwork`, NWM packet APIs are not called.

Observed counts in the focused window:

```text
PullPacket: 0
SendTo: 0
RecvBeaconBroadcastData: 0
HandleSecureData: 0
GetConnectionStatus: 0 in the post-button window
```

Therefore the current best interpretation is:

```text
Room creation succeeds
Beacon loop continues
User presses proceed
Game-side task / event / wait path starts
Before reaching NWM packet APIs, some expected condition is not satisfied
After about 3 seconds, game-side code calls DestroyNetwork
```

The current failure should be treated as post-button / pre-packet-loop failure, not as a `PullPacket` or `SendTo` implementation failure yet.

## Known NWM IPC caller LR values

Use raw `lr` directly in Ghidra for these NWM IPC logs. Do not subtract `0x50000` for IPC caller LR.

```text
GetChannel       lr=0x003645DC
BeginHosting     lr=0x00364A50
SetProbeResponse lr=0x00364A30
DestroyNetwork   lr=0x00364D54
GetConnStatus    lr=0x003651B0
Bind             lr=0x003658D0
Unbind           lr=0x00365E64
Shutdown         lr=0x00365AB4
```

ARM translation/runtime alias traces are separate. Some ARM code-fetch logs use `+0x50000` aliases and may be JIT translation-time only, not proof of actual execution.

## Ghidra anchors already identified

```text
FUN_0033727c  BeginHostingNetwork -> GetChannel success path
FUN_003645a0  thin GetChannel wrapper; calls GetChannel IPC wrapper
FUN_00364d20  DestroyNetwork wrapper; contains DestroyNetwork IPC call
FUN_0033b8bc  room/session setup path; calls FUN_0033727c
FUN_00339994  worker busy/active gate; checks worker + 0x3eec
FUN_00339d8c  worker start; sets worker + 0x3eec = 1
FUN_00339c90  worker stop; clears worker + 0x3eec = 0
FUN_0033c0a0  packet-loop worker; eventually would call receive/pull logic
FUN_0033807c  GetConnectionStatus-driven update path
FUN_00365184  GetConnectionStatus wrapper
```

### `FUN_00339994` interpretation

`FUN_00339994(worker, ..., timeout)` behaves like a busy/active wait gate:

- checks `worker + 0x3eec`
- if `+0x3eec != 1`, returns success immediately
- if `+0x3eec == 1`, waits for a bounded count and can return error `0xe0a14827`

Earlier suspicion around this worker path is useful context, but current button-based logs show the post-button failure happens before new NWM IPC packet activity.

## Important failed/unsafe trace attempt

Do not re-enable intrusive Dynarmic function runtime tracing based on repeated `jit->Step()` inside `ARM_Dynarmic::Run()`.

It caused SIGTRAP / assertion:

```text
server_session.cpp:operator():100: Assertion Failed!
Kernel::ServerSession::HandleSyncRequest
SVC::SendSyncRequest
```

The file `yw2_arm_func_runtime_trace_patch.py` may exist for record/history, but it should not be chained into the build unless deliberately debugging this crash class. Prefer non-invasive IPC/SVC/static tracing.

## Android focused log command pattern

Use a narrow log filter and markers. Avoid generic `Bind|Unbind` grep because it catches Android `Binder` noise.

```sh
mkdir -p ~/yw2_logs
TS=$(date +%Y%m%d_%H%M%S)
FOCUS=~/yw2_logs/yw2_next_clean_$TS.focus.log

su -c 'setprop debug.azahar.yw2_func_trace 0'
su -c 'setprop debug.azahar.yw2_arm_trace 0'
su -c 'setprop debug.azahar.yw2_svc_wait_trace 0'
su -c 'setprop debug.azahar.yw2_status_quiet_host 0'

su -c 'setprop debug.azahar.yw2_nwm_ipc_trace 1'
su -c 'setprop debug.azahar.yw2_trace_level all'
su -c 'setprop debug.azahar.yw2_self_loopback 1'
su -c 'setprop debug.azahar.yw2_bind_pulse 0'

su -c 'setprop debug.azahar.yw2_dummy_node 0'
su -c 'setprop debug.azahar.yw2_dummy_packet 0'
su -c 'setprop debug.azahar.yw2_status_pulse 0'

su -c 'logcat -c'
su -c 'log -t YW2_MARK START_LOG'

su -c 'logcat -v epoch -s CitraNative:W YW2_MARK:I DEBUG:F AndroidRuntime:E libc:F' \
  | grep --line-buffered -E "YW2_MARK|\\(YW2 IPC\\)|\\(YW2 TRACE\\)|\\(YW2 WAIT\\)|DestroyNetwork|Fatal signal|F DEBUG|AndroidRuntime|SIGSEGV|SIGABRT|SIGTRAP|Assertion" \
  | grep --line-buffered -v -E "SendPacket type=0 channel=11 size=435|SendPacket channel11_435|Beacon self-loopback|Bind event pulse" \
  | tee "$FOCUS"
```

Separate session marker/tap pattern:

```sh
NEXT_X=540
NEXT_Y=2050

su -c 'log -t YW2_MARK BEFORE_PRESS_NEXT'
input tap "$NEXT_X" "$NEXT_Y"
su -c 'log -t YW2_MARK AFTER_PRESS_NEXT'
```

After failure:

```sh
su -c 'log -t YW2_MARK AFTER_FAIL'
gzip -9 "$FOCUS"
cp "$FOCUS.gz" /sdcard/Download/
echo "$FOCUS.gz"
```

## SVC wait trace status

A focused SVC wait log was attempted, but no `(YW2 WAIT)` lines appeared. That does not prove the game is not waiting. It more likely means one of:

```text
1. APK did not include the SVC wait trace patch
2. property name / build chain mismatch
3. log level/filter mismatch
4. SVC trace injected into a path not hit by this specific wait
```

Next priority on Android: confirm `debug.azahar.yw2_svc_wait_trace=1` actually produces `(YW2 WAIT)` lines in any known wait scenario. If not, fix the patch chain or log category first.
